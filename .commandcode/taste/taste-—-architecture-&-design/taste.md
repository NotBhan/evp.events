# Taste — Architecture & Design
- External side-effect integrations (e.g. Google Sheets writes) must stay server-side and read server-only env vars, never browser-facing/NEXT_PUBLIC. Confidence: 0.8
- Side effects must run after the primary DB transaction commits — never inside it — and their failure must not roll back the primary operation. Confidence: 0.8
- Rejects fire-and-forget side effects without persisted recovery: sync failures must be recorded (status/attempts/error) and remain retryable. Confidence: 0.75
- External writes must upsert by a stable business key rather than blindly appending duplicate rows. Confidence: 0.7
- Prefers explicit, pinned identifiers/configuration over ambient or active-context resolution — e.g. an Apps Script write must target SpreadsheetApp.openById(id).getSheetByName(tab), never getActiveSpreadsheet()/getActiveSheet(). Confidence: 0.85
- When modifying an existing external write path, preserves the existing destination schema/column layout rather than reshaping it (e.g. keep the existing 11-column layout). Confidence: 0.7
- Prefers keeping API response contracts stable (no breaking changes) unless absolutely necessary, even when a downstream feature would be easier with a contract change or extra exposure. Confidence: 0.75
- Typography: headers and fonts should maintain a proper, consistent character gap — avoids negative/cramped letter-spacing (e.g. `tracking-tight`/`tracking-tighter`) on condensed display faces like Bebas Neue, favoring a uniform positive gap instead. Confidence: 0.7
- Prefers the database as the single authoritative source of truth; external integrations (e.g. Google Sheets) are treated as non-authoritative secondary mirrors that must never be a prerequisite for, or gate, the primary operation. Confidence: 0.8
- For race-prone state transitions (e.g. duplicate-entry prevention), correctness must be enforced server-side via an atomic DB transaction/conditional update; frontend-only guards (disabled buttons, client state) are explicitly not trusted. Confidence: 0.85
- Reuse-first, minimal-change approach: inspects the existing schema/auth/patterns first, extends existing models rather than adding new tables, and reuses established libraries/mechanisms instead of reinventing them; explicitly avoids over-engineering. Confidence: 0.85
- Prefers non-destructive, additive migrations and never resetting the database as part of a feature; does not modify unrelated columns when adding fields. Confidence: 0.8
- Prefers separating a read-only "verify/preview" step from a mutating "confirm/commit" step so that a read or scan never causes a state change on its own. Confidence: 0.7
- When a feature is removed or changed, retains a deprecated DB column rather than dropping it if historical rows or downstream consumers (Sheets, receipts, code) still depend on it — favors non-destructive backward compatibility over schema cleanup. Confidence: 0.7
- Critical state-changing operations require authoritative online validation; does not implement offline/local-first acceptance with later reconciliation (no offline admission). Confidence: 0.7
- When a specification and the actual repository disagree, verifies the real implementation and reports the discrepancy honestly rather than treating two values/formats as equivalent; preserves working behavior and makes the smallest safe change instead of redesigning. Confidence: 0.75
- For rate limiting on serverless deployments, does not rely on process-local in-memory counters as the sole protection; prefers a persistent (e.g. database-backed) mechanism or an existing platform capability. Confidence: 0.7
- Prefers a single responsive web application over separate native/desktop/mobile apps for an internal tool. Confidence: 0.8
- Prefers operational feature toggles (e.g. open/close a booking window) driven by server env configuration rather than requiring a code change or redeploy. Confidence: 0.75
- Timestamps configured via env should carry an explicit timezone offset and must never be inferred from the browser/client. Confidence: 0.8
- Centralizes a cross-cutting business rule in one server-side helper module rather than scattering independent comparisons across components. Confidence: 0.7
- UI controls must be touch-friendly and responsive and must not depend on hover-only interactions. Confidence: 0.7
- Supports hidden service/developer accounts: a dedicated flag on the account record keeps such accounts out of the operator-facing admin panel entirely (excluded from listings and rejecting panel-initiated management actions, e.g. 404) while the account stays fully functional and manageable via CLI/bootstrap tooling. Confidence: 0.7
