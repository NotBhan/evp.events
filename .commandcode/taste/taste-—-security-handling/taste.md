# Taste — Security Handling
- Do not print or expose secrets in output/logs — Stripe secret keys, webhook signing secrets, DATABASE_URL/connection strings, or any full credentials — nor sensitive payment details (card data). Confidence: 0.8
- When reporting on env/config, reports only PRESENT/MISSING (presence/absence) and never the actual value; when an identifier must be shown for comparison, exposes only a safe partial (e.g. last few chars), and redacts endpoint URLs to host only. Confidence: 0.8
- Prefers safe diagnostics that surface identifiers/status/attempt counts over raw payloads or secret values. Confidence: 0.75
- When auditing secrets, does not want a working production secret regenerated or rotated merely to satisfy the audit, and does not want a missing secret silently invented — prefers reporting MISSING and only generating/configuring when the existing workflow explicitly requires it. Confidence: 0.8
- Never weakens existing PII masking/redaction to enable a downstream feature (e.g. checkout prefill): when genuine contact data isn't legitimately available to the client, prefers omitting the field (letting the third party collect it) over unmasking via an endpoint, storing extra copies, or logging it in plaintext. Confidence: 0.9
- Never forwards masked/redacted placeholder values (e.g. `ab****@gmail.com`, `+91 ••••• •6510`) downstream as if they were genuine — detect mask/redaction characters at the boundary and omit them, and never fabricate or infer missing genuine values. Confidence: 0.85
- Credentials/tokens should be opaque and non-guessable (random or signed), stored only as a secure hash at rest, and never encode raw PII or predictable identifiers; the design must prevent ID enumeration. Confidence: 0.8
- Minimizes data in responses: returns only the minimum information the consuming UI needs and avoids full contact (email/phone) or payment details unless operationally necessary. Confidence: 0.7
- Never exposes internal database errors/stack traces to end users; surfaces distinct, clear, operational failure states (machine reason + user-facing message) instead. Confidence: 0.7
- Never lets a predictable/public identifier (e.g. a booking ID) serve alone as an authorization credential — the real credential is the identifier plus a valid cryptographic signature (HMAC), verified with timing-safe comparison. Confidence: 0.85
- Validates and normalizes untrusted input before persisting it (trim/uppercase, enforce a maximum length, restrict to a safe identifier character set) so it never becomes arbitrary, uncontrolled database data. Confidence: 0.85
- Never trusts client-supplied identity/audit fields (e.g. a "who performed this" field like `checkedInBy`); derives them server-side from the authenticated session and ignores any client-provided value. Confidence: 0.9
- Never trusts client-supplied business-critical fields like quantity/unit price/total amount — the server derives price and total authoritatively from the selected item/pass and forces quantity server-side, ignoring any client-provided value. Confidence: 0.85
- Prefers a dedicated server-only secret per concern (QR signing, staff session, customer session, payment secrets all distinct) and never reuses an existing secret for a new credential — blast-radius isolation. Confidence: 0.8
- Keeps authentication domains strictly separated: a staff/organiser session must not authorize the public site and a customer session must not authorize the staff area; each session type gates only its own routes, while a staff user can still use the public flow as an ordinary customer without privilege leakage. Confidence: 0.85
- Prefers individual, revocable accounts (hashed credential, role, active flag) over a shared PIN/credential, so access is independently revocable and actions are attributable to a specific person. Confidence: 0.75
- Cookie-authenticated state-changing endpoints need CSRF/origin protection (retain SameSite=Lax plus server-side Origin/Referer validation), without introducing a large external CSRF framework unless the repository already uses one. Confidence: 0.7
- Credential hashing prefers an existing approved password-hashing dependency; when none exists, uses the platform's built-in scrypt with a per-user random salt rather than adding a new dependency. Confidence: 0.7
- Never hardcodes credentials into source; provisions accounts via a secure bootstrap CLI with hashed credentials instead of committing default secrets. Confidence: 0.7
- Rejects malformed or oversized opaque input tokens up front (explicit size cap) rather than silently normalizing or coercing them. Confidence: 0.6
- Generates secret values with `openssl rand -hex 32` (64 lowercase hex characters) rather than ad-hoc or placeholder values. Confidence: 0.7
